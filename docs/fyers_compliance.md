# FYERS Compliance and API Readiness

Stage 0 research is recorded in `REPOSITORY_AUDIT.md`. Official sources were rechecked on 2026-10-16 for Stage 7. This is a build gate summary, not a determination of legal eligibility for a particular account or setup.

- SEBI's February 2025 framework was extended and applies from 2026-04-01. See [SEBI's September 2025 timeline extension](https://www.sebi.gov.in/legal/circulars/sep-2025/extension-of-timeline-for-implementation-of-sebi-circular-dated-february-04-2025-on-safer-participation-of-retail-investors-in-algorithmic-trading-_96979.html) and the [original SEBI circular](https://www.sebi.gov.in/legal/circulars/feb-2025/safer-participation-of-retail-investors-in-algorithmic-trading_91614.html).
- FYERS says old API apps became data-only on 2026-04-01. API trading requires its new app activation, a mapped static IP, and daily 2FA; its current guidance states up to 10 orders/second and that market orders are converted to MPP orders. See [FYERS activation guidance](https://support.fyers.in/portal/en/kb/articles/how-do-i-activate-the-new-app-for-api-trading-after-april-1-2026) and [FYERS retail-algo summary](https://support.fyers.in/portal/en/kb/articles/what-are-the-new-sebi-rules-for-retail-algo-trading-from-april-01-2026).
- NSE's implementation standards require mapped static IPs and daily session logout, describe a 10 order/second/exchange-segment threshold, require exchange-issued algo identifiers for audit, and require broker RMS/security controls. The [NSE implementation circular](https://nsearchives.nseindia.com/content/circulars/INVG67858.pdf) is primary exchange guidance. NSE's [retail-algo FAQ](https://nsearchives.nseindia.com/web/sites/default/files/inline-files/FAQ_Retail%20Algo_03112025_NSE.pdf) explains distinctions between direct client APIs/tech-savvy investors and vendor platforms and states that algo market orders are not permitted (and IOC/market orders are not allowed in commodity algo trading).
- These descriptions leave an important architecture classification unresolved: this app would ingest TradingView alerts and run Python logic outside FYERS. The exact status of that topology (client-generated/tech-savvy flow vs third-party algo platform), where its logic must run, whether TradingView is treated as a platform/vendor in this chain, required onboarding/empanelment, and the order-tag mechanism must be confirmed by FYERS and the relevant exchange before any transaction transport is implemented. The FYERS summary says third-party platforms must be empanelled and hosted within broker infrastructure; NSE FAQ describes a tech-savvy client path using client-hosted logic and a static IP. Generic text does not decide which category this particular hybrid setup falls into.
- NSE prohibits algo market orders. Although FYERS says its API converts market orders to MPP orders, this contract supports LIMIT only and does not infer that MPP makes market-order strategies eligible.
- FYERS documents API plan-dependent historical intraday and expired F&O access, including request limits. Actual account plan and dataset entitlements remain unverified; see [FYERS API rate limits and plan coverage](https://support.fyers.in/portal/en/kb/articles/what-are-the-fyers-api-rate-limits-for-standard-and-prime-plans).
- FYERS Historical API returns OHLCV candles; that by itself does not establish access to the imported TradingView up/down-volume/delta series or guarantee historical option intraday coverage for the required instruments. See [FYERS History API data fields](https://support.fyers.in/portal/en/kb/articles/how-can-i-get-historical-data-for-a-symbol-over-a-specific-date-range-using-the-history-api).

## Stage 7 transaction contract status

`src/nifty_algo/brokers/fyers_transactions.py` contains the FYERS v3 place/modify/cancel payload contract and a default-deny compliance permit. No real HTTP/SDK transport is implemented or wired into the order manager. Stage tests inject an in-memory fake only. The adapter allows LIMIT only; the order contract uses the v3 documented fields and does not turn an accepted order response into a fill. This is not deployable order execution.

Permit requirements are all false by default and require explicit verification of app activation, static IP, same-day 2FA, FYERS approval of topology, algo ID/tag rules, eligible product/instrument/order types, client and broker order-rate/RMS controls, compliance review, and operator arming. This Python checklist is an engineering fail-closed control; setting its booleans is not proof that the regulator or broker has approved anything. No project code currently creates or populates a ready permit.

These sources do not establish that this exact TradingView webhook → personal Python host → FYERS order path is permitted for the user's account. No account details have been checked, and Stage 7 deliberately supplies no authenticated FYERS transaction transport.

Live trading remains disabled. The Stage 7 transaction contract is mocked and fail-closed; it is not wired into `OrderManager`, `AppConfig`, or the FYERS SDK. Before any real transaction transport is added, confirm the exact deployment classification and permitted host, activated app/permissions, static-IP mapping, daily authentication/logout, exchange algo ID and broker tag mapping, instrument/product/order-type eligibility, per-account/per-segment limits and RMS behavior, and FYERS' exact payload/MPP handling. These are account/deployment-specific gates, not established by generic documentation.
